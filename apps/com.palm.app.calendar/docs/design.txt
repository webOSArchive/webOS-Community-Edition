+ 2010.12.13: Mike Lee: Created DataHub to allow highly decoupled observation/notification:

 	- Allows objects to watch, ignore, and/or share information without direct access to each other.
	- Works with enyo components via published properties (i.e. is24Hr)
	- Works with Non-enyo objects via setPropertyName methods (i.e. setIs24Hr).

	+ Syntax is as follows:

		+ app.watch ({ publishedPropertyName: publishedPropertyOwner }):
			+ Allows the publishedPropertyOwner to watch for information shared using publishedPropertyName.

				i.e. app.watch ({ is24Hr: dayView });	// Allows Day View to receive 24hr clock mode updates.

		+ app.ignore ({ publishedPropertyName: publishedPropertyOwner }):		
			+ Allows the publishedPropertyOwner to ignore information shared using publishedPropertyName.
			
				i.e. app.ignore ({ is24Hr: dayView });	// Allows Day View to ignore 24hr clock mode updates.

		+ app.share ({ publishedPropertyName: [informationArray] }):
			+ Shares the informationArray with every publishedPropertyName watcher passing informationArray as parameters.

				i.e. app.share ({ is24Hr: { data: true }});	// Shares 24hr clock mode state with all is24Hr watchers.

		+ NOTES:

			+ If you'd like the shared value to be kept and shared with any late watchers use this syntax:

				app.share ({ property: { data: value, keep: true }});

+ 2011.9.14: Henry Hughes: Notes on new CacheManager solution for Dubonnet+:

	- Does not currently listen for accounts changed, it probably should at some point to enable further ratelimiting on databaseChanged
	- There is no way to cancel queries in the current implementation. I ran into issues with the design and allowing queries to be cancelled
	  as it was pretty much a surefire way to desynchronize the timestamp cache from the event cache. At some point this should be revisited
	  as it does improve performance pretty drastically if you allow cancellations.

	  I think there may be some intractable issues here though due to the design of the cache. If a databaseChanged query is cancelled by
	  a databaseChanged query, it shouldn't be too disasterous as the later query should be able to complete the work the first one would have
	  required. However if a databaseChanged query is cancelled by a getDays query, things can go badly wrong here because databaseChanged queries
	  try to populate all instances of a set of events throughout the cache, while getDays queries try to populate additional days for all events.
	  The problem arises because a getDays query isn't going to know that the cache is missing events as-is, and will attempt to populate
	  for the days its looking for only while leaving all prior days out of sync with reality.
